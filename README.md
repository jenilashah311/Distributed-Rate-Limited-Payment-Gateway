# Resilient Distributed Payment Gateway (SDE Interview Sandbox)

A high-performance payment gateway prototype built in Go, designed to solve critical distributed systems challenges: **exactly-once execution (idempotency)** and **traffic throttling (rate limiting)** under concurrent load. 

This project is structured specifically to serve as a deep-dive discussion piece for **SDE system design and team-matching interviews at companies like Google**.

---

## 🌟 System Architecture

```
[ Client / Dashboard UI ] --(1) Send Request--> [ Redis Sliding-Window Limiter ]
                                                           |
                                             (2) Allowed (Within Limit)
                                                           v
[ PostgreSQL DB ] <--(4) Write Idempotency Key-- [ Go Microservice (Goroutines) ]
        |                                                  |
(5) Unique Key OK                                  (3) Process Payment Logic
        v                                                  |
[ 200 OK Response ] <--------------------------------------+
```

### 1. In-Memory Traffic Throttling (Redis Sliding-Window)
Protects downstream billing processors from DDoS attacks, API client loops, and retry storms. It runs an atomic **Lua Script** on Redis to execute a sliding-window counter in under 1 millisecond before database queries occur.

### 2. Transaction-Safe Deduplication (PostgreSQL Idempotency Keys)
Guarantees that a user is charged **exactly once**, even if the client double-clicks the purchase button or automatically retries due to a flaked network connection.

### 3. Lightweight Concurrent Handler (Go Runtime)
Uses Go's `M:N` scheduler (goroutines) to handle thousands of concurrent requests simultaneously with minimal CPU and memory overhead (starting at just 2KB of memory per request).

## 🚀 Key Engineering Problems Solved

### A. Atomicity & Race Conditions in Rate Limiting
* **The Problem:** Performing checking and writing operations sequentially across separate Redis commands introduces race conditions (Time-of-Check to Time-of-Use).
* **The Solution:** We implement the sliding-window algorithm inside a single **Redis Lua script**. Since Redis runs Lua scripts atomically in a single thread, the operation is 100% thread-safe without requiring application-level locks.

### B. "Double-Charging" Under Concurrent Requests
* **The Problem:** In a distributed environment, multiple servers might process identical payment requests at the same millisecond. Traditional `SELECT` followed by `INSERT` suffers from read-write race conditions.
* **The Solution:** We use PostgreSQL's **ACID guarantees and UNIQUE constraints** on a UUID `idempotency_keys` table. The Go handler attempts an insert immediately inside a transaction. If a concurrent duplicate request beats it, Postgres throws a Unique Violation error (`23505`). Our Go code catches this error, rolls back the transaction, and safely reads/returns the response generated by the winning thread.

## 🛠️ Technology Stack
* **Language:** Go (Golang) - high-performance concurrent runtime.
* **Cache:** Redis - in-memory data store for sub-millisecond throttling.
* **Database:** PostgreSQL - ACID-compliant database for transaction safety.
* **Orchestration:** Docker & Docker Compose - containerized local sandbox.
* **Testing:** Python - automated concurrent stress-testing.

## 🎓 SDE Interview Talking Points (Google Level)

When discussing this project in system design or team-matching interviews, you can showcase depth in these areas:

* **Distributed Lock vs. Optimistic Concurrency:** Explain why using database constraints is more scalable than holding a distributed lock (e.g. Redlock), which incurs network roundtrips and complex lease-time edge cases.
* **Redis Memory Consumption & TTLs:** Explain how in production you would implement table partitioning or automatic background pruning (e.g., keeping idempotency keys active for only 24 hours) to keep index lookups fast.
* **Graceful Failure Modes:** What happens if the payment goes through, but the database write fails? (Discuss transition states: writing the key with a `STARTED` state, updating to `SUCCESS` after the charge, and using a reconciliation queue for mismatches).

## 💻 Running the Sandbox locally

### 1. Launch Services
Start the Go application, Redis, and PostgreSQL database:
```bash
docker-compose up --build -d
```

### 2. Open the Interactive Dashboard
The Go web server serves a live dashboard at:
**[http://localhost:8082](http://localhost:8082)**

You can use the dashboard to trigger:
* **Single Payments**: Returns a standard `Cache MISS`.
* **Double-Clicks**: Shows the first request returning a `MISS` and the duplicate returning a cached `HIT`.
* **Concurrent Races**: Fires 5 requests simultaneously, resulting in exactly 1 `MISS` and 4 `HIT`s.
* **Rate-Limit Spams**: Fires 15 requests in rapid succession, showing the first 10 requests allowed and the subsequent 5 throttled with `429 Too Many Requests`.

### 3. Run Automated Tests
You can also run the verification suite from your terminal:
```bash
python3 test_client.py
```
